Architecture guide

How Chief of Staff and Agent Grid work (and work together)

A guided tour of two local programs: Chief of Staff (the assistant you talk to) and Agent Grid (the dashboard that runs your Claude Code and Codex agents). It explains what each one is made of, how Chief of Staff drives Agent Grid, and where the edges are.

Written against Chief of Staff 6fc6e92 and Agent Grid 3ecd6f8 (September 2026). File paths are relative to each repo root: ~/Desktop/chief-of-staff and ~/AgentGrid. When the code and this document disagree, the code wins.

The same document in Markdown: docs/how-chief-of-staff-and-agentgrid-work.md. Self-contained: works offline, loads nothing from the network.

#The one-minute version

  • Chief of Staff (CoS) is a personal assistant for your Mac. You talk to it (or type) in a small floating "pill". A local Node.js server sends what you said to a language model, which can call tools: read your calendar, run a terminal command, or work with your coding agents.
  • Agent Grid (AG) is a local Python dashboard over every Claude Code and Codex session on the Mac. It finds sessions, starts new ones, chats with them, and keeps a ticket board. Its orchestrators are standing managers that start agents on their own.
  • CoS is a client of AG's HTTP API. CoS never runs claude or codex itself. When you say "have an agent add a quiz to module 6", CoS asks AG to start that agent.
  • They find each other through one file: ~/.agentgrid/web.json. AG writes its address and a secret token there, and CoS reads it.
  • Traffic goes both ways. CoS sends requests to AG (JSON over HTTP). AG pushes status changes back over a live stream (GET /api/events), which is how CoS can tell you when an agent is done.
  • Everything stays on this Mac. Both servers listen on 127.0.0.1 only.
  • No agent framework. Neither uses LangChain, LangGraph or an agent SDK. Each has a small hand-written loop, and the coding itself is done by the Claude Code and Codex CLIs (section 5).

#1. The big picture

How to read it: you talk to the menubar app. It shows the pill page, which sends your words to the local server. The server runs the tool-use loop against your chosen model. When the model asks for an Agent Grid tool, the client calls AG's HTTP API. AG does the work: it starts CLI processes, sends chat turns, runs orchestrators, and edits tickets. Separately, AG's poller notices status changes and streams them back to CoS's watcher.

#2.2 The menubar app (Swift)

  • AppDelegate.swift wires everything up. It builds the ✦ menu, including the Agent Grid submenu (drawn from GET /api/grid), and relays messages between the page and native code.
  • ServerManager.swift starts node <runtime>/dist/cli/cos.js ui --port <port> --no-open if nothing answers yet. It pings GET /api/projects until the server is up. Port 4747 is the default, or the next free one (ShellConfig.swift). Server output goes to ~/.cos/logs/menubar-server.log.
  • PillPanel.swift is a borderless floating window with a WKWebView that loads http://127.0.0.1:<port>/?shell=1&mode=pill.
  • HotkeyMonitor.swift handles double-tap Control (talk) and ⌥Space (type).
  • SpeechListener.swift runs Apple's on-device speech recognition. WakeListener.swift and WakePhrase.swift listen for the wake name.

The bridge between Swift and the page works in both directions:

  • Page → Swift: window.webkit.messageHandlers.shell.postMessage({type: "listen" | "hide" | "height" | …}).
  • Swift → page: panel.eval("cosShell.transcript(text, isFinal)"), cosShell.status(...), cosShell.dismiss(). window.cosShell is defined in src/ui/web/app.js.

#2.3 The local server (Node.js)

src/ui/server.ts uses plain node:http, with no framework. cos ui binds it to 127.0.0.1 on port 4747 (COS_UI_PORT or --port change that). The endpoints that matter here:

EndpointPurpose

When the server starts listening, it also starts the Agent Grid watcher (section 10.4), because cos ui passes the agentWatch option.

#2.4 Voice in and voice out

  • Hearing: Apple's on-device recognizer in the menubar app. In a plain browser (cos ui), the page uses the browser's Web Speech API instead. No API key is needed for either.
  • Speaking: src/voice/tts.ts. It uses OpenAI's TTS when OPENAI_API_KEY is set, otherwise the Mac's say. Audio plays through a small native player, src/voice/player/cos-play.swift.

#2.5 The brain: one tool-use loop

runIntent() in src/brain/loop.ts is the heart of CoS. For each message it:

  1. Builds memory context: the ledger, journal, calendar and git activity (src/core/context.ts), plus summaries of recent conversations (src/brain/recall.ts).
  2. Picks a prompt template for the intent (src/brain/prompts/*.md): ask, focus, capture, wrap or brief.
  3. Picks the tools that intent may use (toolsFor() in src/brain/tools.ts). Agent Grid tools are only available to ask and focus.
  4. Calls the model through a provider-neutral interface (src/brain/llm/types.ts). Adapters live in src/brain/llm/anthropic.ts and openai.ts. OpenRouter and OpenAI-compatible servers use the OpenAI adapter. registry.ts chooses which one to use.
  5. If the model asks for tools, it runs each one through ToolRuntime.execute(), appends the results, and asks again. It stops at a final answer or after 12 turns.

The conversation is saved in ~/.cos/conversations (src/brain/conversation.ts). Besides user and assistant turns there are **event turns**: things that happened outside the chat, like "you tapped Start agent" or "agent X finished". The next message to the model starts with (Since your last reply: …), so the model knows about those events.

#2.7 Guard rails: access modes and pending actions

CoS decides what it may do on its own. The model doesn't get to decide.

Access modes (src/actions/access.ts, saved in ~/.cos/access.json, changed with cos access):

CapabilityDefaultoffaskauto
agents (all of Agent Grid)askEvery AG tool fails with "Agent Grid access is off". The watcher hangs up.Reads run freely. Anything that changes something waits for your OK.Changes run straight away, except ticket deletes and orchestrator approvals.

Pending actions (src/actions/pending.ts): when a change needs your OK, the tool doesn't run it. It queues a Pending with a random id, a one-line label, the exact details, and a button word ("Start agent"). The tool then returns an instruction to the model, like "Not started yet. Ask them in one short sentence…". The reply carries a confirmation card.

There are three ways to answer:

  1. Tap the button: POST /api/actions/confirm {id} → performPending() (src/actions/perform.ts).
  2. Say a clear yes or no: before the model even runs, settlePending() in server.ts uses readConsent() (src/actions/consent.ts) to recognize "yeah, send it" or "no, leave it", and acts on it.
  3. Give a mixed answer ("yes, but make it shorter"): this goes to the model, which may call confirm_pending. That tool must be the model's first call in its reply.

Pending actions are single-use, expire after 5 minutes, and live in the server's memory. The model can't confirm its own request: only a button tap or your words can. repeated() in tools.ts also refuses to queue the same action twice, or to redo one that ran in the last 15 minutes.

#3. Agent Grid, layer by layer

#3.1 What runs

python3 -m agentgrid --web from ~/AgentGrid (or ag --web through bin/ag) calls serve() in agentgrid/web.py. It uses only Python's standard library: no pip, no build step. It starts:

  • a **Fleet** poller thread that refreshes the list of sessions every 2 seconds (POLL_SECONDS);
  • a **ThreadingHTTPServer** on 127.0.0.1:8787, or on a free port if 8787 is taken;
  • a **ChatManager** (agentgrid/chat.py) for chat turns with sessions;
  • a **RunManager** (agentgrid/orchestrator_run.py) for orchestrators. On startup it resumes any run the last shutdown interrupted;
  • a small thread that keeps ~/.agentgrid/web.json pointing at this run (section 4.1).

Plain ag shows the same data as a curses grid in the terminal (agentgrid/ui.py). CoS only talks to the web server.

#3.2 The security gate

Every request must carry the per-run token, either as ?t=<token> or in the X-Agentgrid-Token header. Handler._authorized() compares it with secrets.compare_digest. Anything else gets 403 {"error": "Bad or missing token."}. Responses also send X-Frame-Options: DENY and Referrer-Policy: no-referrer. The token is new every time AG starts.

#3.3 Finding sessions: discovery.py

AG doesn't scrape screens. discovery.collect() combines:

SourceGives
claude agents --json --allWhich Claude sessions exist, and their state or status, cwd, pid, job id
Transcripts on disk (~/.claude/projects/…/*.jsonl, read incrementally)Title, model, last prompt, tool counts, last activity
~/.claude/jobs/<id>/state.json → tempoWhether a background job is really working right now

normalize_status() merges the CLI's two vocabularies into one. Background sessions report working/blocked/done/failed/stopped; interactive ones report busy/idle/waiting, which become working/idle/blocked. Fleet._as_json() is the session shape CoS receives from /api/sessions: sessionId, title, customName, status, engine, model, cwd, project, prompt, idleSeconds, ….

#3.4 Starting agents: launch_agent() and spawn_agent()

Both the New agent sheet (POST /api/spawn) and an orchestrator's start_agent tool go through launch_agent() in web.py. That's why an agent an orchestrator started looks exactly like one you started by hand.

launch_agent():

  1. Checks the work area exists (areaId).
  2. If ticketKey is set, puts the ticket's handoff brief (tickets.handoff_prompt) in front of the task. The brief includes the ag ticket commands the agent should use to report back.
  3. Resolves the folder. noProject: true means ~/Desktop (or ~ if there's no Desktop); otherwise it uses cwd.
  4. Calls spawn_agent(). That refuses any folder that isn't a known project (discovered git repos, folders the fleet already works in, or folders added by hand). It also refuses a model id that isn't well-formed.
  5. Registers the area membership, assigns the ticket (moving it to In progress), and names the session once it appears.

spawn_agent() has three shapes:

ShapeCommandNotes
Claude, background (default)claude --bg [--model M] <prompt> in the folderPrints a job id, which AG uses to name the session later.
Codex, backgroundcodex exec --cd <dir> -s workspace-write --skip-git-repo-check [-m M] <prompt>, detachedPrints no job id, so the name is matched by folder and start time.
Interactive (macOS)A Terminal.app tab running claude <prompt> or codex <prompt>Every argument is shell-quoted. Opened through AppleScript.

A model AG hasn't seen on this Mac is checked for up to 10 seconds. If the CLI refuses it, AG says so and starts nothing. Spawned agents get AGENTGRID_AGENT=<name> in their environment, and OPENROUTER_API_KEY is removed from it (agent_env()).

#3.5 Talking to a session: POST /api/chat → chat.py

A message to an existing session is a new headless turn of the CLI, resumed on that session:

  • Claude: claude -p <message> --output-format stream-json --verbose --permission-mode <posture> --resume <sessionId>
  • Codex: codex exec -s workspace-write -c approval_policy="never" resume --json … <sessionId> <message>

cwd always comes from the session AG tracks, never from the caller. The default posture is auto, which maps to --permission-mode bypassPermissions. CoS sends no posture, so it gets this default. One turn runs per session at a time. Messages sent during a turn wait in a queue.

#3.6 Transcripts: GET /api/transcript?id=

transcript.render_blocks() turns the session's JSONL file into typed blocks: {kind: user|assistant|tool|result|thinking, text, name, gist, error}. The file is opened read-only, so reading a live session is safe. CoS uses these blocks for get_agent_output and to quote an agent's last words when it finishes.

#3.7 The event stream: EventHub and GET /api/events

EventHub in web.py is the push side of the integration.

  • After every 2-second poll, Fleet._announce() shows the snapshot to EventHub.observe(). The snapshot includes live chat turns, so a session AG is chatting with counts as working.
  • For each session whose status changed since the last poll, it creates an event:
    id: 3f9a2c1d-7
data: {"type":"status","sessionId":"…","title":"Refactor auth","engine":"claude",
       "cwd":"/Users/you/Desktop/my-app","project":"my-app",
       "from":"working","to":"done","finished":true,"at":"2026-09-15T18:40:12"}
  • finished is true when the session was working and settled into done, failed, blocked, idle, stopped or complete.
  • Ids look like <run>-<n>. The run prefix changes on every AG restart. The last 200 events are kept. A client that reconnects with Last-Event-ID from the same run gets every event it missed, and no event twice.
  • A : ping comment is sent every 15 seconds as a heartbeat.

#3.8 Work areas and tickets

  • Areas (agentgrid/areas.py, ~/.agentgrid/areas.json) hold the list of areas and a members map from session id to area. An area doesn't list its agents directly. That's why CoS's gridboard.ts does the join.
  • Tickets (agentgrid/tickets.py, one JSON file per ticket under ~/.agentgrid/tickets/) have a per-project key and number (APP-12), five statuses, type, priority, assignee, labels and an activity log. Agents use the ag ticket … CLI (agentgrid/ticket_cli.py) to take, comment on and move tickets from their own shell.
  • Assigning to a live session (/api/tickets/assign) also sends the ticket's handoff brief into that agent's chat (through ChatManager). An assignment to a bare name is just a label.

#3.9 Orchestrators

An orchestrator is not a session. It's a manager that starts sessions. Its code is split up:

FileRole
agentgrid/personas.pyWho it is: guidelines, the OpenRouter model it thinks with, agent defaults, allowed models, team, skills, lessons.
agentgrid/orchestrator.pyWhere it works (a posting): scope (a work area, or "" for all), project, mode ask/auto, limits. Data and files only: no network, no threads.
agentgrid/orchestrator_brief.pyWhat the model is told: the system prompt and the tool menu.
agentgrid/orchestrator_run.pyHow it behaves: the loop, gates, limits, persistence, watching its agents.
agentgrid/openrouter.pyThe one network call: tool_turn() to OpenRouter. The key comes from the macOS Keychain (credentials.py), or from OPENROUTER_API_KEY on other systems.
ServerHost in web.pyThe orchestrator's only door to the machine. Each method is something the UI can already do.

The tool menu the orchestrator's model gets: list_projects, list_work_areas, create_work_area, start_agent, list_agents, read_agent_output, send_to_agent, wait_for_agents, list_tickets, create_ticket, move_ticket, comment_ticket, set_plan, remember, message_user, read_skill, read_prompt, finish. There's no shell, no filesystem access and no editor.

The run loop (Run._step()):

Key rules, all enforced in code (none of this is left to the model):

  • Approval gates (_gate_reason): in ask mode, start_agent and create_work_area wait for you. In auto mode, opening an interactive Terminal tab still asks, unless the persona's default is interactive. A request that would be refused anyway (a model outside the allowed list, say) is refused outright, without asking you.
  • Limits (defaults): 3 agents at once, 20 agents per run, 200 steps, $5 of the orchestrator's own OpenRouter spend. The agents it starts run on your normal Claude Code and Codex logins.
  • Durability: after every step the state is written to ~/.agentgrid/orchestrators/<id>/state.json, with an append-only journal.jsonl beside it. A pending approval survives a restart. A run interrupted mid-step resumes, and the model is told to check list_agents and list_tickets before starting anything, so it doesn't start the same agent twice.
  • Statuses: idle, running, waiting (needs you), done, failed, stopped.

#4. How the two connect

#4.1 Finding each other: ~/.agentgrid/web.json

Details that matter:

  • The override. AGENTGRID_URL=http://127.0.0.1:8787/?t=… in CoS's environment replaces the file (findConnection() in src/actions/agentgrid.ts).
  • Loopback only. CoS refuses any base URL other than http://127.0.0.1 or http://localhost.
  • Read every time. CoS calls findConnection() per request (and per event-stream connection), so an AG restart with a new token is picked up without restarting CoS.
  • Two AG instances. A second ag --web (a test run on a spare port, say) won't take the file from a run that still answers GET /api/ping with its own token. CoS keeps talking to the first run.

#4.2 The request contract

AgentGrid.call() in src/actions/agentgrid.ts:

  • GET when there is no body, otherwise POST with a JSON body.
  • Headers: X-Agentgrid-Token: <token>, plus content-type: application/json on POSTs.
  • Timeout: 15 s, or 90 s for /api/spawn, because starting an agent (and checking its model) can take a while.
  • Errors come back in plain words:
What happenedWhat CoS says
Connection refused"Agent Grid isn't running. Start it with python3 -m agentgrid --web from ~/AgentGrid."
No web.json"Agent Grid hasn't shared its connection yet…"
403"Agent Grid rejected the key: it was probably restarted…"
404 on /api/events or /api/orchestrators"This Agent Grid can't … yet: update it from ~/AgentGrid and restart it."
Other non-2xxAG's own {"error": "…"} text, e.g. "That directory is not one of the known projects."

#5. Frameworks and components: what's custom, what's borrowed

Short answer: neither codebase uses LangChain, LangGraph, LlamaIndex, CrewAI, AutoGen, the Claude Agent SDK or any other agent framework. Both dependency lists and all imports were checked. Agent Grid's agentgrid/teams.py even says so in its docstring: "No SDK, no API key, no LangGraph -- Claude Code already is the agent; this only decides who runs, in what order, and what each one is told."

Every loop in the system is hand-written and short. The hard part of "being an agent" (reading code, editing files, running a shell) is done by the Claude Code and Codex CLIs. Agent Grid launches them, feeds them turns, and reads what they write to disk, but treats them as black boxes.

#5.3 What this means in practice

  • There is no graph runtime. Nothing checkpoints or plans on your behalf. Each loop is a while with explicit exits, and its state is plain JSON you can open. CoS keeps conversations in ~/.cos/conversations. AG keeps each run in ~/.agentgrid/orchestrators/<id>/state.json.
  • Swapping models is cheap. CoS talks to every provider through one small interface. AG's orchestrators only need an OpenRouter model id.
  • Agent quality belongs to the CLIs. Neither program changes how Claude Code or Codex reason or use their tools. AG only controls what they are asked, in which folder, with which flags, and when.

#6.1 Chief of Staff: runIntent()

             + { user: "(Since your last reply: …)\n\n<what you said>", images? }

up to 12 times:
  res = provider.chat({ model, instructions, context, messages, tools, serverTools,
                        json?, effort, maxTokens: 16000 }, onText)
  refusal  → throw RefusedError
  pause    → keep going (a provider-side tool paused mid-answer)
  no calls → stop
  for each tool call, in order:

Details worth knowing:

  • Errors stay inside the loop. ToolRuntime.execute() catches every exception and returns Error: <message> with isError: true. The model reads the failure and can adjust, for example "Agent Grid access is off. They can turn it on with cos access agents ask."
  • Replay within a run. providerData carries Anthropic thinking blocks, or OpenRouter reasoning details, back to the same provider on the next turn.
  • Replay across messages. steps (the tool calls and results, without provider data) are saved with the reply. Later, historyMessages() replays at most 12 exchanges and 24,000 characters, and cuts each tool result to 1,500 characters.
  • Anthropic specifics. The system prompt goes in as two blocks. The first (persona and task) has cache_control: ephemeral, and the second holds memory. Models that support it get adaptive thinking plus the COS_EFFORT level. The morning brief asks for JSON through output_config.format.
  • OpenAI-compatible specifics. Tools go in as {type: "function", function: {…}}. The JSON brief uses response_format with strictSchema(), and the request is retried without it if a server rejects it.
  • Web search. It's a server-side tool: Anthropic's web_search tool, or openrouter:web_search. The provider runs it, and CoS never sees the call. OpenAI's own endpoint and local servers go without. Only the ask and focus intents get it, limited to 3 results and 4 searches.

#6.2 Agent Grid: an orchestrator Run

POST /api/orchestrators/start ─► Run.start(goal)
    state = blank_state() + {status: running, goal, messages: [system, "Goal: …"]}
    _spin() ─► one worker thread (guarded by _active) ─► _work(): while not cancelled: _step()

_step():
    an approval was answered?  → _apply_decision(): run or decline the held call, then the rest of that turn
    _drain_inbox()             → your messages become user turns
    _limit_hit()               → steps ≥ max_steps or cost ≥ max_spend_usd → _finish("failed")
    messages[0] = system_prompt(_context())             rebuilt every step from persona and posting
    turn = openrouter.tool_turn(trim_messages(messages), persona.model, tool_specs(context))
    steps += 1, costUsd += usage.cost, _persist()
    no tool calls → _after_prose(): watch busy children for free, or status = waiting
    else _run_calls():
        start_agent? → _shape_start(): fill engine, model and mode from the persona's defaults
        _gate_reason(call) → _request_approval(): status = waiting, pending saved, worker exits
        otherwise _invoke(call) → Run._tool_<name>(args) → _record_result() (≤ 20,000 characters)
        finish called → _finish("done")
  • Threads. HTTP threads call start, stop, submit, approve and decline. One worker thread per run makes the model calls. _wake (a threading.Event) cuts a wait short when you send a message, and _cancel handles stop. A worker that has nothing to do exits, and the next action restarts it.
  • Context. trim_messages() always keeps the system prompt and the goal. It fills up to 120,000 characters with the newest messages and drops tool results whose call was cut off.
  • Durability. orchestrator.write_state() runs after every change. At startup, RunManager.resume_all() restarts interrupted runs. repair_messages() removes a half-finished tool turn, so a side effect is never repeated blindly.
  • Failures. A tool that raises ValueError returns {"ok": false, "error": …} to the model. Any other exception becomes "That tool failed on this machine." with no traceback. OpenRouter errors fail the run. The provider's own error text isn't passed on, because it can echo the request back.
  • Free waiting. _watch() checks the board every 3 seconds (WATCH_POLL_SECONDS) with no model calls. _tell_model() wakes the model with the change and the last 1,500 characters of the agent's output.

#6.3 Agent Grid: driving the CLIs (chat.py)

ChatManager keeps one ChatSession per session id. send() queues a message, and _drain() runs turns one at a time. _run_turn() starts the CLI as a subprocess in its own process group, so it can be cancelled cleanly, and reads its output line by line. normalize() and normalize_codex() turn each JSON line into one small vocabulary: turn_started, assistant_message, thinking, tool_use, tool_result, turn_done, error. The board streams these from GET /api/chat/stream.

CoS doesn't subscribe to that stream. It sees a chat turn only indirectly: _overlay_chat() marks the session working in /api/sessions and /api/events, and the transcript grows on disk.

#6.4 Agent Grid: team pipelines (teams.py, workflows.py)

A team is a JSON pipeline of nodes, and each node is a persistent ChatSession. Prompts are templates over {input} and {node_id}, and loops jump back to an earlier node while a marker such as NEEDS_WORK appears, up to a set number of times. workflows.DraftManager turns a written description into a team draft. CoS has no tools for teams.

Dispatch. ToolRuntime.execute(name, input) calls dispatch(), a single switch. An unknown name throws Unknown tool "<name>", which goes back to the model as an error. Two lists label the results. #8. How Chief of Staff knows about Agent Grid, and how it calls it

#8.1 No runtime discovery: a contract kept by hand

CoS never asks AG what it can do. AG has no MCP server, no OpenAPI description and no capability endpoint that CoS reads. /api/orchestrators does return a capabilities field, but CoS ignores it. The integration is a contract kept in step by hand:

  • Routes and JSON shapes are hard-coded in the AgentGrid class and its TypeScript interfaces: AgentSession, Ticket, Board, AreasFile, Orchestrator, OrchestratorPending, AgentEvent. Comments point at the AG files they mirror ("Agent Grid's areas.py and tickets.py").
  • Vocabularies are mirrored: TICKET_STATUSES, TICKET_TYPES, TICKET_PRIORITIES, ORCHESTRATOR_STATUSES, and STATUS_ALIASES ("mirrored from tickets.py"). The model-id pattern MODEL_ID matches AG's models.MODEL_RE.
  • Older AG versions are tolerated. models() returns null on a 404, so exact model ids still pass through. orchestrators() and events() turn a 404 into "update Agent Grid". get_work_areas still shows areas when the ticket board can't be read.
  • Tests stand in for AG. fakeAgentGrid() in tests/agentgrid.test.ts is a small node:http server that plays AG, token check included, on a random local port.

If AG changes a route or a field, CoS keeps compiling. The mismatch shows up at runtime, as an error message or an empty list.

#8.2 What the model knows, and where from

  1. Tool descriptions in TOOLS. This is the main source.
  2. The persona, src/brain/persona.ts, which explains when to use the terminal and when to start an agent, how to pass model names, what an orchestrator is, what "needs you" means, and to always confirm approvals by voice.
  3. Tool results, as ready-made text. CoS never hands raw AG JSON to the model. formatSessions(), formatTranscript(), formatAreaTree(), formatTickets(), formatOrchestrator() and formatModels() produce short lines, with ids cut to 8 characters.
  4. Name matching happens in code. The model passes what you said ("the auth agent", "Opus 5", "the Product Manager"). findSession(), findOrchestrator(), findTicket(), findArea() and resolveModel() turn it into exact ids, or return an error that lists the options.

#10. End-to-end flows

#10.1 "Do any of my agents need me?"

Nothing changes, so nothing waits for your OK.

#10.2 "Start an agent on Opus 5 to review the export code" (ask mode)

Variations:

  • **auto mode**: steps 5 to 9 are skipped, and the tool calls grid.start() directly.
  • **area / ticket**: the tool resolves the name to an areaId or ticketKey first. AG then puts the ticket's brief in the prompt, registers the area and moves the ticket to In progress.
  • **visible: true**: AG opens a Terminal tab instead of a background agent.
  • No folder: noProject: true, and AG runs the agent in ~/Desktop.

#10.3 "Tell the auth agent to also update the tests"

  1. message_agent → GET /api/sessions → findSession() matches by id prefix, or by title, custom name or project words. If several match, it prefers the one that is working or needs you. Otherwise it asks you for the id.
  2. In ask mode the message is queued, and CoS reads it back to you ("Should I send this to …?").
  3. On yes: POST /api/chat {sessionId, message}. AG's ChatManager runs claude -p <message> --resume <sessionId> … in that session's folder. The turn is queued if one is already running.
  4. While that turn runs, the session shows as working. When it ends, the event stream reports a finish (10.4).

#10.4 An agent finishes, and you hear about it

Reliability details (src/actions/agentwatch.ts):

  • Reconnects: waits 3 s, doubling up to 60 s. Silence longer than 45 s counts as a dropped connection, since AG sends a heartbeat every 15 s.
  • Nothing twice: it remembers the last 500 event ids it announced. AG replays what was missed after Last-Event-ID, but only within the same AG run.
  • Respects access: with cos access agents off it doesn't connect, and it hangs up within about 5 s if access is switched off while connected.
  • Terminal version: cos agents --follow prints the same stream.

#10.5 Orchestrators: start, then approve from CoS

Two things to notice:

  • An orchestrator's waiting status means one of two things. If pending is set, it's holding a tool call for your approval: answer with respond_orchestrator_approval. If pending is null, it ended its turn in plain text and wants a reply: answer with message_orchestrator. formatOrchestrator() shows which one it is.
  • Agents an orchestrator starts are ordinary sessions. Their finishes come through /api/events and get announced by CoS like any other agent's.

#11. Boundaries and limitations

#Trust and safety boundaries

  • Same Mac only. Both servers bind 127.0.0.1. CoS refuses a non-loopback AG address. To reach an AG running on another machine, use an SSH tunnel to a local port and set AGENTGRID_URL.
  • The token is AG's lock. It's minted per run and stored owner-only in web.json. CoS only uses it in request headers and in the signed-in board link that the ✦ › Agent Grid menu opens. **CoS's own server has no token and doesn't check the request's Origin.** It relies only on the loopback bind. That is a weaker posture than AG's, and worth knowing if the CoS server ever does more.
  • CoS never runs the agents. Every start, message or ticket change goes through AG's API and AG's checks.
  • Your OK is enforced in code, not asked of the model. Access modes plus single-use, expiring pending actions. The model can't confirm its own request. Orchestrator approvals and ticket deletes always ask.
  • The project boundary is wider from CoS. AG only spawns in known projects. But CoS's start_agent first adds any folder inside your home folder as a project, creating it if needed. From CoS, the effective boundary is "anywhere under ~". CoS refuses folders outside home.
  • Agents run with broad permissions. A background spawn passes no permission flag, so the CLI's own settings apply. Follow-up messages through /api/chat, which message_agent and ticket assignment both use, run with posture auto → --permission-mode bypassPermissions for Claude, and approval_policy="never" for Codex. Once sent, a message's tools run without asking.
  • Orchestrators never get a shell. They get a fixed tool menu executed by AG, limits enforced by AG before each call, and the same spawn path as a human.
  • Secrets stay put. CoS keeps its model keys in ~/.cos/.env and doesn't send them to AG. AG's OpenRouter key lives in the Keychain, is never sent to the browser, and is removed from every spawned agent's environment.

#Functional limitations

  • Missed finishes across restarts. Replay after a dropped stream only works within the same AG run, and for the last 200 events. If AG restarts, anything that finished while CoS wasn't listening isn't announced. You can still ask ("did the auth refactor finish?").
  • Events come from a 2-second poll. A status that changes and changes back within one poll isn't seen. The watcher only runs while CoS's server runs and agent access isn't off.
  • Orchestrators aren't pushed to CoS. CoS doesn't subscribe to /api/orchestrators/stream, so an orchestrator that starts waiting for approval won't notify you through CoS. You find out by asking, or from AG's own badge.
  • CoS can operate orchestrators, not configure them. Creating or editing orchestrators, personas, models, limits or mode happens in AG's UI. CoS also can't edit a pending approval's arguments before approving. AG's UI can.
  • Pending confirmations are short-lived. They're held in the CoS server's memory: they expire after 5 minutes and are lost if the server restarts. Just ask again.
  • Messaging a Claude agent mid-turn is risky. AG's own code notes that resuming a Claude session that is still running starts a copy the real agent never sees. AG blocks this for orchestrators (follow_up_block) but not yet on /api/chat, which is what CoS uses. It's safest to message agents that are idle, done or need you.
  • Codex quirks. No job id, so names are matched by folder and start time. No attach. A chat is refused while a terminal or another run holds the Codex thread (HTTP 409).
  • Interactive agents need macOS Terminal.app. On other hosts, AG only offers background agents.
  • Model names. AG's model list only includes models this Mac has used, plus aliases. An exact id it hasn't seen goes through, and AG checks it for up to 10 seconds when starting.
  • Size limits. CoS shows the model the first 15 sessions (the ones that need you and the working ones come first) and about the last 10,000 characters of a transcript, and says when it has left something out.
  • Test coverage. Per the CoS README, the orchestrator read path was checked against a live AG. The write path (start, stop, send, approve) is unit-tested against a mocked server only.
